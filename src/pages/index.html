Abydos

A terminal-first IDE for AI and cloud development.

The terminal is not a strip at the bottom of an editor. It is where the work happens — shells, tmux windows, agents, a program running in a pod — and the editor, the debugger and the cluster arrange themselves around it. Native AppKit: no web view, no Electron, no subscription.

macOS 14 or newer, Apple silicon. Signed with a Developer ID and notarised.

The two claims

Everything else here is an editor doing what editors do. These two are why it exists, and both are ordinary to use rather than a mode you enter.

Debug your program where it actually runs

A launch configuration with one extra key builds for the cluster's architecture, pushes the binary into a development pod and runs it there — about a second, against the minutes an image build and a rollout cost. The pod has the real chart's config, its secrets, its service account and its sidecars, so the program finds what production would give it.

Then press debug. It stops on your breakpoint in the pod, in your own sources, because the binary was compiled on this machine and its debug information names these files. A JVM is held suspended until you attach, so a worker cannot finish before you arrive.

Agents as sessions, not as a sidebar

An agent session is a PTY the app owns rather than something a view owns. It can be hidden, shown again, or handed over for manual takeover, and its process keeps running throughout.

Results come back over MCP as typed data — file, line, severity, detail — arriving as the work proceeds, so a click goes to the line. Scraping a rendered screen would break the first time the tool restyled its output; this is a contract instead.

One field at the top of the window

The titlebar is a capsule: which project on the left, which branch on the right, a hairline between them, and ⇧⌘P written on it. Press that and a field opens underneath it, on the thing it is about. The shortcut is VS Code's on purpose — a decade of it has taught everybody's hands where a palette lives, and muscle memory is worth more than a free letter.

Everything, in one list

Typing searches projects, the branches of the repository that is open, and the commands. A project opens; a branch is checked out where the branch menu would have put it; a command runs. Projects are found on disk as well as in the recents, so the case a switcher exists for — opening something for the first time — is the case it handles.

> for commands, : for a line

VS Code's prefixes, in the same field. > narrows to commands; : takes a number and puts the caret on that line of whatever is open. The placeholder says so, because a prefix nobody knows about is a prefix nobody uses.

The menu bar is the list

The commands are not a list kept beside the menus — they are the menus, read at the moment you ask. Each row carries the menu it lives in and the key it already answers to, so the palette teaches the shortcut instead of replacing it. Anything greyed out in the menu is absent here: a palette is what can be done now.

A line that means one thing

Under the titlebar is a seam that is coloured only while something is running, and red if it failed. It holds still rather than sweeping — a bar that crawls is claiming a percentage nothing here knows — and it carries no other meaning, which is what lets it be absent the rest of the time.

And the rest of an IDE

Terminal

A real PTY with a VT100/xterm emulator: colour, mouse reporting, the alternate screen, kitty graphics, and a bundled Nerd Font. ⌘J opens one, ⌘⏎ gives it the whole window, and the panel's tabs can be tmux's windows.

abydos some-file.md typed in one of them opens that file in the editor of this window and puts the keyboard in it, getting the terminal out of the way if it was covering it. The pane's own file descriptor is what says which window asked, so nothing has to be installed and nothing has to be configured.

Editor

tree-sitter highlighting and folding for 24 languages, a persistent rope behind the text, and a parser that is allowed to land a frame late so typing never waits for it.

⌘/ comments the lines a selection touches, at the indent they share; a completion that came with holes in it is stepped through with ⇥; and ⇧F6 renames through the language server — worked out in full before anything is written, across every file it touches, and undone by one ⌘Z.

Diagrams

A .puml, a .mmd and a .drawio open with the drawing beside the source, and a fence in a Markdown file is drawn where it stands. Mermaid is the real Mermaid, in the app rather than in a container — 3.6 MB of JavaScript against 2.16 GB of headless browser — and what it hands back is flattened into plain geometry, so the picture in the pane, the one in Export ▸ SVG and the one a browser draws are the same picture.

draw.io is the whole editor, not a viewer: the shapes are dragged in the tab, and the document stays the app's — the edited dot, ⌘S and the file watcher work as they do for text, and a file that arrived compressed is written back compressed. Diagrams follow the theme the app is wearing, so a dark window does not hold one white rectangle.

Models, pictures and PDFs

A file written in order to make a shape opens showing both: an OpenSCAD .scad beside its render, and a .scad that will not compile shows no shape at all rather than the last one that did. A go3mf recipe is the exception and opens as its text, with the model offered rather than drawn — a recipe is an assembly, so its model is every part's render and a go3mf build on top of them, which is the slowest preview here.

An STL or a 3MF opens in the viewer, a picture opens at the size it was taken and zooms to the pixels, and a PDF opens as a PDF. A preview nobody has looked at costs nothing — arrowing through a directory of models renders none of them.

Cadova: a model that is a program

A Cadova model is Swift, and opens with the shape beside the code. A .swift is a model when the package above it declares an executable target that depends on Cadova and this file is one of that target's sources — the manifest is the only place that says so, and neither the name of the file nor its contents can.

Which means the shape is not read but run: swift run in the package root, the pane carrying the build's own last line while it goes, and the compiler's complaint in place of the model when it will not build. Any of the target's sources rebuilds it, because a helper file changes the shape as much as the one with the model in it; a burst of saves is one rebuild; and no build is killed to make way for a newer one, since a half-stopped swift build makes the next one a cold one. The file is rewritten in place, so turning the part round to see what changed survives the rebuild.

Run and debug, here too

Launch configurations, Makefile goals, Maven goals, Gradle tasks, Bazel targets, Conan commands, a Swift package's executables and its swift test, and entry points found by scanning. Breakpoints — conditional, hit counts, log points — over DAP, with stack, variables and watches.

Tools out of an image

A checkout can say where its tools come from. .abydos/tools.json names an image per tool and is checked in, so what draws a diagram in a repository is that repository's business and a machine that never installed the tool gets the same answer as everybody else. Settings say the same thing for one person across every project, and the file wins where both speak.

Apple's container by default, because it needs no daemon running before it will answer — or Docker, nerdctl or podman, which all take the three flags this needs. Said rather than guessed: ask for Docker and have none and you are told so, instead of quietly getting the other one. Whatever is already installed is still used first. An image a machine has not got is fetched before it is first needed, and one this app ships a recipe for is built here rather than pulled.

The container the project says it is worked on in

A checkout carrying a devcontainer.json is offered its own toolchain: the language servers run inside that container, so the problems on screen are the problems from the build rather than from whatever this Mac happens to have installed.

Asked for rather than done — one question, once per project, at the moment something needs it. A pill beside the project's name says a container is in use, and its menu lists the ones the repository has, moves the servers between them, or gives the work back to this machine.

Navigator

Version-control colours, lazily-loaded directories, a warm tint on build output, and full keyboard navigation. FSEvents keeps it live, so a git checkout in a terminal recolours it. Files are made, renamed, dragged, copied and thrown away in the tree itself — named on the row rather than in a dialog — and ⌘Z takes any of it back.

What the project depends on

The tree has a second root, where IntelliJ puts External Libraries: the packages this project depends on, named as packages and each saying which version and where it came from. Swift packages, Go modules, Cargo, npm — pnpm and yarn as themselves — Maven, Gradle, Bazel and Conan.

Read off what is already on disk. No cargo metadata, no npm ls, no Gradle: a tree row is not worth starting a build tool for, and Conan's recipe is a Python program that filling in a row should not be running. A lock file that cannot be made sense of says so, which is a different sentence from a project that depends on nothing.

Git

Status, changes, history, blame, branches, worktrees, stash and push. The branch is in the titlebar, and a worktree keeps the repository's name and gains a chip beside it — asked of git rather than read off the path, since a worktree can be made anywhere. The other checkouts of the repository are in that same control, and choosing one opens it as a project.

The working copy is shown as the folders it changed rather than as a flat list of paths: a folder stages everything under it and says how much of itself is on this side of the index. Changes are thrown away from the unstaged side only, and the sheet says how much it is about to take and which of it is a deletion rather than a revert.

Profiler

CPU, heap, goroutine, block and mutex profiles with a flame graph — pointed at a program here, or at a pod in the cluster through a forwarded port.

Swift apps, on the device in your hand

An Xcode project's schemes appear beside everything else that can be run, and a submenu says where: this Mac, a simulator, or a phone — over the cable or over Wi-Fi, whichever it is paired by. Where a scheme went last is remembered, so the play button repeats it.

It builds, installs, launches, and the app's own output arrives in the terminal. No Xcode window, and nothing to keep in step with one.

A backlog the app, the terminal and an agent all read

Everything left to do is markdown in .abydos/backlog/, in a folder per state. ⇧⌘B shows it as a list or a board, the abydos-backlog command works it from a shell, and an agent moves the same files. There is no database and no server, so the three of them cannot disagree about where an item stands. A project keeping openspec/changes instead is shown that, from the same button.

An item picked up gets a worktree of its own, and its card reads the checklist, the estimate and the pictures out of that checkout — 3/6 in the worktree, and what the branch thinks is left. The card opens the worktree as a project, or a shell in it.

Results you work through, not results you read

A project-wide search and a Find Usages both answer in the bottom panel, in a list that is a checklist: rows are marked done as you look at them, several at a time, struck through where they stand while the heading counts off 2/3. It touches nothing on disk, ⌘Z takes back the last marking, and a mark survives the search being run again.

The keyboard stays in the list — ↓ shows each result without leaving it — and the list can sit under the editor, beside the project view, or in a window of its own, which is remembered.

Three themes, six palettes — or one of your own

The app's own amber one, the blue-grey it started with, or Dracula at upstream's own values. Each has a daylight half — a separate question, so following the system does not cost you the theme you chose. All six are the same interface photographed six times — see them. A scheme is a JSON file now, so a seventh is one dropped into ~/.config/abydos/schemes.

1 jdtls answers for .java. A Kotlin file is highlighted and folded but not served, and its main functions are still found, run and debugged — the JVM does not care which language produced the class.
2 A pom.xml or Gradle build file has no server, and its grammar knows nothing about modules — so ⇧⌘O over one is answered by that build file's own parser: modules, plugins, dependencies, tasks.
3 Every language folds, by one of two routes. Where the grammar ships a folds.scm — or one is written here, as Java's is — the fold points are the ones that query names. Where it does not, they are derived from the parse tree: any node spanning more than one line. The derived set is the larger of the two and the named set is the tidier, which is a difference in taste rather than in support.
4 Two servers, and a project says which in .abydos/tools.json. jdtls is the default and is type-aware: it reads the build file for the classpath, so it knows a call has the wrong argument type — and importing a five-hundred-bundle reactor is minutes and gigabytes first. kmp-lsp indexes source instead, with no JVM and no type checking at all. On Eclipse's eclipse.platform.ui — 143 bundles, 7,566 files — it was answering go-to-definition across bundles at 2.6 seconds, where jdtls on the same symbol was still silent at ten minutes holding 3.97 GB. Debugging works either way: jdtls is started for the debugger alone when you press Debug.

PlantUML, Mermaid and draw.io are not in the table, because what there is to say about a diagram is that it is drawn rather than that it is coloured. A .puml is served by plantuml-lsp all the same, the way a .scad is by openscad-lsp.

Nothing is bundled. A language server, a debugger and a build tool each have opinions about your toolchain, and the ones already on your machine are the right ones — so what is missing is named in a bar at the top of the editor, with the one command that installs it. Where more than one server answers for a language, the project says which it wants and where it comes from — installed here, or an image — and the footer says which one actually answered and what chose it: the project's file, your settings, or this app's own default.

And nothing has to be installed for a project to be read. What a build file offers comes out of the file, not out of the tool: a BUILD file's *_binary and *_test rules are the targets, and which Conan commands make sense follows from whether there is a conanfile.py or only a conanfile.txt — a list of dependencies has nothing to build, so it is not offered. bazel query would be the more correct answer and is also a build-graph load that wants Bazel present and can take a minute, which is too long to spend filling in a menu. Neither recipe is executed to ask it what it contains. The commands are the tools' own, so running one without the tool fails the way it always does, rather than in a way this has to explain.

Java, in full

The most recent language to be supported end to end, and the one that shows what "supported" means here:

The language server

brew install jdtls. Each project gets an index of its own, and the JDKs installed on the machine are reported to it, so a module targeting 17 compiles against 17.

Or the other one. A repository that is five hundred bundles can say {"languages": {"java": "kmp-lsp"}} and get a syntactic server that has the whole thing navigable in seconds — no JVM, no reactor import, and no type checking at all. It is a trade, it is written down where the choice is made, and Debug still starts jdtls, because the classpath is only there.

Maven and Gradle

Read directly — modules, plugins, dependencies, tasks — so their goals are run configurations and ⇧⌘O works over a build file. The wrapper wins over anything on the PATH.

Debugging

java-debug is not a program but a bundle the language server loads: jdtls is asked for a debug session, answers with a port, and the classpath comes from the same server, because nothing else knows it.

In a cluster

A jar is built here and pushed into a pod that has a JVM. Debugging starts that JVM suspended with JDWP open, so the attach lands before the program has done anything — which is the only way to debug a worker.

Three decisions do most of that: a persistent rope whose interior nodes sum bytes, UTF-16 units and newlines; highlighting scoped to the bytes on screen; and a parser that runs off the main thread and is allowed to land a frame late. The rope is authoritative for text, the parser only for colour.

Building it yourself

# Xcode's Swift, not whichever one is first on the PATH.
git clone https://github.com/philipparndt/abydos.git
cd abydos
make          # build the .app and launch it
make test     # the suite
make dev      # debug build, in the foreground, logs on the terminal
