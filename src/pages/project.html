Getting around a project

One field for everything the app can be asked to do, a tree that shows what the project depends on as well as what is in it, and lists that are worked through rather than read.

One field at the top of the window

The titlebar is a capsule: which project on the left, which branch on the right, a hairline between them, and ⇧⌘P written on it. Press that and a field opens underneath it, on the thing it is about. The shortcut is VS Code's on purpose.

Everything, in one list

Typing searches projects, the branches of the repository that is open, and the commands. A project opens; a branch is checked out; a command runs. Projects are found on disk as well as in the recents, so opening something for the first time is a case the switcher handles.

> for commands, : for a line

VS Code's prefixes, in the same field. > narrows to commands; : takes a number and puts the caret on that line of whatever is open, and the placeholder says so.

The menu bar is the list

The commands are not a list kept beside the menus — they are the menus, read at the moment you ask. Each row carries the menu it lives in and the key it already answers to, so the palette teaches the shortcut instead of replacing it. Anything greyed out in the menu is absent here: a palette is what can be done now.

The navigator

Version-control colours, lazily-loaded directories, a warm tint on build output, and full keyboard navigation. FSEvents keeps it live, so a git checkout in a terminal recolours it. Files are made, renamed, dragged, copied and thrown away in the tree itself — named on the row rather than in a dialog, with ⌘Z taking any of it back, including out of the trash. A trashed row goes in the same event as the key, before the trash is even asked, because a row that stays put for a cross-process round trip is one somebody presses again. New is a submenu of the kinds of file this project actually has, so the extension is not typed out again every time.

A row with a version-control state carries a dot at its trailing edge in that state's colour, files and folders alike — a colour on the name alone is only legible against the names beside it, so a run of untracked files reads as a tree of green text and one modified file among forty is a word in a slightly different colour. A folder's state is already the roll-up of what is under it, which is what makes the mark worth having on a collapsed one. Nothing is drawn for unmodified or ignored rows: in a project with a build directory those outnumber everything else, and a mark on nearly every row is furniture.

What the project depends on

The tree has a second root, where IntelliJ puts External Libraries: the packages this project depends on, named as packages and each saying which version and where it came from. Swift packages, Go modules, Cargo, npm — with pnpm and yarn named as themselves, since the lock file beside package.json is what says which of the three installed it — Maven, Gradle, Bazel and Conan.

Read off what is already on disk: no cargo metadata, no npm ls, no mvn dependency:list. A lock file that cannot be made sense of says so, which is a different sentence from a project that genuinely depends on nothing.

Git, from the titlebar

The branch is in the titlebar, and a worktree keeps the repository's name and gains a chip beside it — asked of git rather than read off the path, since a worktree can be made anywhere. The repository's other checkouts are in that same control, and choosing one opens it as a project. Everything the app does with a repository is behind ⌘2 and has a page of its own: one tree, two pages, and a real branch left behind before anything destructive runs.

The terminal and the project follow each other

The window follows the terminal

Follow the terminal's project, in Settings, and off until it is asked for: when the shell in the pane in front moves to another project, the window changes to that project. New windows start the way the setting says, and each window can still be switched by hand afterwards.

What makes it bearable to leave switched on is what does not count as moving. cd Sources is somebody going about their work, so a directory inside the project changes nothing — and inside the project is not the same as inside the repository around it, since a project opened at a subdirectory of a checkout has a repository above it that answers for every directory in it. So the question is asked about the project: a directory outside it is a move, a directory belonging to no repository at all leaves the window where it is, and a shell that walks out into something else is followed.

The switch itself is remembered now, wherever it is flipped: the control on the panel used to change the window's own copy and never write the preference, so every launch read the stored false and a new version was simply the launch somebody noticed. And a window follows the shell's own directory, which is why a script that changes directory several times over one install no longer drags the window through every one of them: cd is a builtin, so a typed one always moves the shell and a running command never does.

And the window arrives with what that project had. A switch captures the editor session, the terminals and which of them was in front, the tmux window, which subproject was open, the selected run configuration, where each Xcode scheme last went, the breakpoints, which sidebar tool was showing, what was folded in each of the trees, any log, commit or stash page that was open — and the commit message somebody was halfway through typing.

Every one of those was lost for a reason worth stating: a fold set lived on the view that drew it, and the sidebar is thrown away and rebuilt on a project switch, a second or two after a window opens, and when a tool shown over the terminal is put away — so the working copy re-folded under somebody who had unfolded it thirty seconds earlier. The folds travel as two lists per tree rather than one, because the trees disagree about what an absent key means: a refs tree arrives open and records what was shut, while origin and Tags arrive shut and record what was opened. A stash page is remembered by its commit and not by its index, since stash@{0} is a different commit after one git stash push.

The terminal reaches the window

abydos some-file.md, typed in one of these panes, opens that file in the editor of this window and puts the keyboard in it. The pane's own file descriptor is what says which window asked — nothing is installed, no port is listened on, and no lock file is written — and the terminal page has the mechanism. The backlog goes the same way: a card offers to open its item's worktree as a project, or a shell already in it.

Lists you work through

Search and usages, in one shape

A project-wide search (⇧⌘F) and Find Usages both answer in the bottom panel, in a list that is a checklist: rows are marked done as you look at them, several at a time, struck through where they stand while the heading counts off 2/3.

It touches nothing on disk, ⌘Z takes back the last marking, and a mark survives the search being run again.

And keep the keyboard

The list arrives with the keyboard in it and nothing opened yet; ↓ shows each result without leaving the list. It can sit under the editor, beside the project view, or in a window of its own, and which of those is remembered. A single usage is not a list at all — it is the place to go, so the file opens at that line.

A backlog three things read

Everything left to do is markdown in .abydos/backlog/, in a folder per state. ⇧⌘B shows it as a list or a board, the abydos-backlog command works it from a shell, and an agent moves the same files. No database and no server, so the three cannot disagree about where an item stands.

An item picked up gets a worktree of its own, and its card reads the checklist out of that checkout — 3/6 in the worktree. A project keeping openspec/changes instead is shown that, from the same button.

The agent that gets handed one of those items, and the session it runs in, are the terminal page.
