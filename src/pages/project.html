Getting around a project

One field for everything the app can be asked to do, a tree that shows what the project depends on as well as what is in it, and lists that are worked through rather than read.

One field at the top of the window

The titlebar is a capsule: which project on the left, which branch on the right, a hairline between them, and ⇧⌘P written on it. Press that and a field opens underneath it, on the thing it is about. The shortcut is VS Code's on purpose — a decade of it has taught everybody's hands where a palette lives, and muscle memory is worth more than a free letter.

Everything, in one list

Typing searches projects, the branches of the repository that is open, and the commands. A project opens; a branch is checked out where the branch menu would have put it; a command runs. Projects are found on disk as well as in the recents, so the case a switcher exists for — opening something for the first time — is the case it handles.

> for commands, : for a line

VS Code's prefixes, in the same field. > narrows to commands; : takes a number and puts the caret on that line of whatever is open. The placeholder says so, because a prefix nobody knows about is a prefix nobody uses.

The menu bar is the list

The commands are not a list kept beside the menus — they are the menus, read at the moment you ask. Each row carries the menu it lives in and the key it already answers to, so the palette teaches the shortcut instead of replacing it. Anything greyed out in the menu is absent here: a palette is what can be done now.

The navigator

Version-control colours, lazily-loaded directories, a warm tint on build output, and full keyboard navigation. FSEvents keeps it live, so a git checkout in a terminal recolours it. Files are made, renamed, dragged, copied and thrown away in the tree itself — named on the row rather than in a dialog, with ⌘Z taking any of it back, including out of the trash. New is a submenu of the kinds of file this project actually has, so the extension is not typed out again every time.

What the project depends on

The tree has a second root, where IntelliJ puts External Libraries: the packages this project depends on, named as packages and each saying which version and where it came from. Swift packages, Go modules, Cargo, npm — with pnpm and yarn named as themselves, since the lock file beside package.json is what says which of the three installed it — Maven, Gradle, Bazel and Conan.

Read off what is already on disk. No cargo metadata, no npm ls, no mvn dependency:list, and not Gradle, which was expected to be the kind that forced the rule and turned out to be the kind that needs it least. A lock file that cannot be made sense of says so — a Conan 1 conan.lock, a pnpm-lock.yaml with no version — which is a different sentence from a project that genuinely depends on nothing, and both are better than an empty list.

Git, as the folders it changed

Status, changes, history, blame, branches, worktrees, stash and push. The working copy is shown as the folders it changed rather than as a flat list of paths: a folder stages everything under it, and says how much of itself is on this side of the index. Changes are thrown away from the unstaged side only, and the sheet says how much it is about to take and which of it is a deletion rather than a revert.

The branch is in the titlebar, and a worktree keeps the repository's name and gains a chip beside it — asked of git rather than read off the path, since a worktree can be made anywhere. The repository's other checkouts are in that same control, and choosing one opens it as a project.

Lists you work through

Search and usages, in one shape

A project-wide search (⇧⌘F) and Find Usages both answer in the bottom panel, in a list that is a checklist: rows are marked done as you look at them, several at a time, struck through where they stand while the heading counts off 2/3.

It touches nothing on disk, ⌘Z takes back the last marking, and a mark survives the search being run again — so a file that gains one new match comes back with that match under it rather than staying finished.

And keep the keyboard

The list arrives with the keyboard in it and nothing opened yet; ↓ shows each result without leaving the list. It can sit under the editor, beside the project view, or in a window of its own, and which of those is remembered. A single usage is not a list at all — it is the place to go, so the file opens at that line.

A backlog three things read

Everything left to do is markdown in .abydos/backlog/, in a folder per state. ⇧⌘B shows it as a list or a board, the abydos-backlog command works it from a shell, and an agent moves the same files. No database and no server, so the three cannot disagree about where an item stands.

An item picked up gets a worktree of its own, and its card reads the checklist and the estimate out of that checkout — 3/6 in the worktree. The card opens it as a project, or a shell in it. A project keeping openspec/changes instead is shown that, from the same button.

The agent that gets handed one of those items, and the session it runs in, are the terminal page.
