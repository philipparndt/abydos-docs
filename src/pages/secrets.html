Secrets

Screens get shared — a call, a review, a demo — and the .env that was open a minute earlier puts its API keys in front of everyone watching. The reflex of closing the file comes after the leak.

Covered by default

macOS gives an app no reliable signal that its window is being captured, so this cannot wait for one. In .env, .env.*, *.env and *.dec, everything after the separator is erased in the row's own background, behind one fixed twelve-column pill.

Nothing about the value survives, its length included. A cover the width of the secret tells a room how long the secret is. Keys, export prefixes, comments and empty values stay readable — reading those is usually why the file is open.

One lock, for the whole file

At the left of the status bar, with View ▸ Reveal Secrets as its other handle. Clicking a cover reveals nothing. Per-value click-to-reveal was built and reviewed out: a click is exactly what a presenter does absentmindedly, on the screen being watched.

A rendering, not a transformation

Offsets, the caret, undo, find and copy all see the real text — copying a value copies the value, which puts nothing on a screen. Typing into a covered value stays covered, the way a password field takes input.

A block scalar is covered whole

Per-line classification cannot see a YAML block scalar: its value lives on the lines after the indicator, which is how a covered pk: | came to sit above a private key in the clear. The roles are computed over the whole file instead.

And it covers itself again

Five idle minutes and the covers go back on. A document left unlocked in a background window is the leak they exist for, and it is the case nobody remembers to close. Scrolling counts as touching the file.

SOPS, from the status bar

A file whose contents carry ENC[ values and a top-level sops key gets a chip beside the lock. Pressing it runs sops --decrypt into the buffer as one edit; ⌘S pipes the buffer back through sops --encrypt under the file's own name, so the project's .sops.yaml rules pick the same keys.

  • Nothing decrypted touches a disk. The plaintext exists in the document's rope and its undo stack and nowhere else. No auto-save, no language server, nothing in the session file — helmsec dec writes a .dec beside the original and SOPS's own editor mode writes a temp file, and this does neither.
  • A save that changed nothing writes nothing. Every sops --encrypt takes a fresh data key, so ⌘S out of habit on a file you only read used to change every line of the diff.
  • Edits survive a project switch, parked in memory by repository and file, and never written to disk.
  • Quitting asks — Encrypt and Save, Discard, Cancel, per file. It is the first quit-time gate this app has had.

Two things to know. A whole-file encrypt changes every value's ciphertext, so the diff of a one-line edit is every line. And sops runs with the app's own environment: it finds an age key where it always does, but a SOPS_AGE_KEY_FILE set in a shell profile is not seen by a GUI app.

Whether git can see it

Covering the values says nothing about the worse exposure: that the file is about to be committed, pushed and read by everybody who clones the repository. A file whose values are covered is asked about — two git runs of one path, off the main thread, and none at all for an ordinary file.

What comes back stands beside the lock: Not in .gitignore, or Committed to git for the case a .gitignore line can no longer fix. Nothing is shown for a file git ignores, which is most of them.

  • The notice is a control. Pressing it adds the file to .gitignore and asks the question again, so the notice goes by itself. A tracked file's menu says git already tracks it rather than offering a fix that is not one.
  • And the chip's other side. Where a rule in the project's .sops.yaml matches, a plaintext file's chip reads SOPS · encrypt. With no rule that matches there is no chip: most files are not meant to be encrypted, and an editor that asked about each of them would be answered by rote.

The status bar this lives in is the editor page.
