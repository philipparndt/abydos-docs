Pull requests

Reviewing somebody's code means reading code, and this is a program for reading code. The half that was missing was never the diff viewer.

A review of anything non-trivial used to be done twice: once in the browser to see the diff and leave the remarks, and once here to understand what the diff did. In a browser there is no language server, no go-to-definition, no outline, no running the tests.

The list

It is opened to answer one question — what is waiting on me — so the ones this account has been asked to review are marked and sorted to the top. Every row says the number, the title, the author, the branch, whether it is a draft and how far along its checks are: a pull request whose build is red is usually not worth reading line by line yet.

  • Teams count by default. user-review-requested:@me and review-requested:@me are different questions, and which one a repository wants cannot be worked out from here — but the narrow answer is the one that is silently empty.
  • Its own button on the rail, beside the git one. What is behind that one is a tree of things this repository holds; a pull request is on somebody else's server.
  • Asked for, never polled. The other git panes re-read on every filesystem event because git is local and cheap. This is a network call against a rate limit.

Reading one

The change against where it branched from

Not the difference between two tips. A file the base branch moved underneath the author is not a file they touched. One open pull request against cli/cli: three files changed, on a base that had gained 29 commits touching 17 files since it branched.

The diff can be the whole file

A browser shows three lines either side. Here the file is on disk with a language server pointed at it, and the question a reviewer has is usually about the code around the change. The hunks are spliced back in at the head, so the same view draws it with honest line numbers.

Made of what the other pages are made of

The same file outline, arrangements, line counts and keyboard as the log and the commit view. A second arrangement of the same thing is how two lists come to disagree about what a rename looks like.

Nothing here stages anything

The diff view offers staging by line because the changes pane needs it. On somebody else's branch that is meaningless, and a menu item that cannot work is worse than none.

Ticks that die

Files are ticked as they are read, through the checklist the search results and the usages list already use. The ticks are remembered per pull request and outlive the window.

A tick dies when the file it was about changes. They are recorded against that file's diff, not against the head commit, and that choice is the whole feature: a rebase that changed nothing keeps its ticks, and a force-push that rewrote one file clears exactly that one. Clearing everything on every push would make a pull request pushed to five times impossible to finish, and the reviewer would learn to ignore the ticks.

Reading it in place

The branch can be checked out as a worktree beside the project, so the language server, go-to-definition, the outline and the tests all point at the change under review. Two can be open at once, which is what a blocked morning looks like.

It is a switch rather than a door: the page does not move when it is pressed — not the file, not your place in it, not what you had ticked or written. A checkout made for a review says so, and finishing with one removes it; a reviewer who opens three a day otherwise grows a checkout a day, each named after a stranger's branch.

Answering

The remarks already on a pull request are drawn at the lines they were left on. A reviewer who cannot see them says again what somebody has already said, and the author has two conversations about one line. A remark whose line has gone is kept and marked as being about an earlier version.

Remarks go on a line or a run of lines — pointing at the first line of a five-line mistake makes the author find the other four — and are sent in one submission with a verdict. That is how GitHub models it and how a reviewer thinks.

The head the page was read at travels with the review. If the author has pushed since, that is said before anything is sent: a remark that lands on the wrong line is a remark about somebody else's code, in the reviewer's name. What is written stays written until the submission succeeds — a review that looks sent and is not is the failure that matters.

Through gh

Every request goes through the GitHub CLI: already authenticated, already handling Enterprise hosts and SSO and token refresh, and a process like git, so it costs no dependency. A token kept here would be a second place for a credential to leak from and a second thing to expire silently.

The cost is stated rather than hidden. A missing gh, one that is not logged in, and a remote that is not a forge this understands are three first-class answers, each saying what to do: 

The GitHub CLI is not logged in to ghe.example.com.
Log in with `gh auth login --hostname ghe.example.com`.

None of them may render as an empty list. "No pull requests are open" is a sentence about the repository and "the CLI is not logged in" is a sentence about the machine. A blank pane cannot tell them apart, and only one is something a reader can act on.

Pull requests across an estate of submodules are on the git page. Having an agent review the branch instead is the terminal page.
