Run and debug

What a project can run is found rather than configured, and pressing debug stops the program where it actually runs — which for a service is a pod in a cluster and not this laptop.

Found, not configured

Open a project and the run list already has things in it, because a build file says what it can do and that is enough. Makefile goals, Maven goals, Gradle tasks, every *_binary and *_test in a BUILD file, what a Conan recipe can be asked for, a Swift package's executable products and its swift test, an Xcode project's schemes, main functions found by scanning, and a .vscode/launch.json imported as it stands.

And every one of them is read rather than run. bazel query is the more correct way to ask what targets exist, and it is also a build-graph load that wants Bazel installed and can take a minute — too long to spend filling in a menu. A conanfile.py is a Python program and a Package.swift is a Swift one; asking either means compiling and running somebody's build script to draw a menu, and swift package dump-package writes a .build directory into the project as a side effect. So the text is read, and what reading cannot see — an executable whose name is computed rather than written — is an entry missing rather than an entry that does not work.

Breakpoints that are more than a place

Conditions, hit counts and log points, over the Debug Adapter Protocol, with the call stack, the variables and watches. Delve for Go, LLDB for the compiled languages, and for Java a bundle the language server loads rather than a program of its own — jdtls is asked for a debug session, answers with a port, and the classpath comes from the same server because nothing else knows it.

Where the program actually runs

Into a pod, in about a second

A launch configuration with one extra key builds for the cluster's architecture, pushes the binary into a development pod and runs it there — against the minutes an image build and a rollout cost. The pod has the real chart's config, its secrets, its service account and its sidecars, so the program finds what production would give it.

And stops there

Press debug and it stops on your breakpoint in the pod, in your own sources — because the binary was compiled on this machine and its debug information names these files. A JVM is held suspended with JDWP open until you attach, so a worker cannot finish before you arrive, which is the only way to debug one.

Profiles, here or there

CPU, heap, goroutine, block and mutex profiles with a flame graph, pointed at a program on this machine or at a pod in the cluster through a forwarded port.

Swift apps, on the device in your hand

An Xcode project's schemes appear beside everything else that can be run, and a submenu says where: this Mac, a simulator, or a phone — over the cable or over Wi-Fi, whichever it is paired by. Where a scheme went last is remembered, so the play button repeats it. It builds, installs, launches, and the app's own output arrives in the terminal — no Xcode window, and nothing to keep in step with one.

A line that means one thing

Under the titlebar is a seam that is coloured only while something is running, and red if it failed. It holds still rather than sweeping — a bar that crawls is claiming a percentage nothing here knows — and it carries no other meaning, which is what lets it be absent the rest of the time.

Which languages can be run, debugged and taken to a cluster is the languages page. Nothing is bundled: Delve, LLDB and a build tool each have opinions about your toolchain, and the ones already on your machine are the right ones — so what is missing is named in a bar at the top of the editor, with the one command that installs it.
