3D Modelling

Some files are written in order to make something else. A .puml is written to make a diagram; a .scad, and the Swift in a Cadova model, are written to make a shape. For those the work is checking one against the other, so both halves are on screen from the moment the file opens and neither has to be asked for.

Nothing here is a format this app parses. A .scad is rendered by OpenSCAD, a Cadova model by building and running the program it is, and a recipe by go3mf — each by the tool whose file it is, so what you see is what that tool makes and not this app's reading of it. What Abydos adds is when to run them, where to put what they write, and what to show when they fail.

Four kinds of file

FileWhat it isHow it opensWhat it needs
.scad an OpenSCAD model source and shape, side by side OpenSCAD
.swift a Cadova model — when the package above it says so source and shape, once the build has run a Swift toolchain
.yaml a go3mf recipe — when its head says it is one as its text, with the model offered go3mf, and OpenSCAD for the parts
.stl, .3mf a mesh — no readable source to show rendered, whole —

Nearly always the name decides. Where it cannot, the file is not guessed at from a distance: the one question that needs an answer is asked once, when the file is opened, and everything afterwards is told rather than asked — so the tab bar's control, the View menu and the editor cannot disagree about what a file is.

OpenSCAD

A .scad opens split, model on the right, and re-renders when the file is saved. openscad-lsp answers for it like any other language server — completion, problems, and ⇧⌘O over the file — which is worth saying because OpenSCAD has no manifest to look for. A model is a file and a project is a directory of them, so anywhere a .scad is opened is a place that server can answer.

Cadova

Cadova models are written in Swift, and this is the one kind of file here whose question is not "what is in it". Every other preview routes on a name — a .puml is a diagram, an .stl is a mesh — and a .swift says nothing at all, because nearly every .swift ever written is not a model.

So the signal is the manifest, which is the only place that says Cadova out loud, and the unit is the target, which is what gets built and run: a .swift is a model when the package above it declares an executable target that depends on Cadova and this file is one of that target's sources. Asking costs a walk up to Package.swift and one read of it — no subprocess, and nothing at all for a file that is not in a package.

The shape is run, not read

swift run in the package root writes a 3MF, and that is what the model half shows. Where it landed can only be learnt from the run — Cadova names the file after the model inside the code rather than after the target — so the pane reads the path out of what the run printed.

It says what it is doing

A build takes seconds and can fail, so the pane carries the build's own last line while it goes — one line, truncated in the middle, with the indicator above it rather than through it — and shows what the compiler said in place of a shape that would not be the one the code describes.

Every source counts

Running the target is what makes the shape, so a helper file changes it as much as the one with Model("hexholder") in it. The pane watches all of them, and watches them on disk, because the compiler reads the disk and an unsaved buffer would show the last save.

A burst of saves is one rebuild

And a change arriving mid-build is honoured when that build ends. No build is ever killed to make way for a newer one: a half-stopped swift build leaves its build directory inconsistent, and the next build of that package is a cold one.

The camera stays where you left it

The file is rewritten in place, so a rebuild that writes the same path leaves the view alone. Turning the part round to look at what changed is the work, and a viewer rebuilt from nothing would put the camera back.

And the Finder stays down

Cadova reveals what it wrote when a build finishes, which is friendly from a terminal and hostile from a pane that rebuilds on every save. The run is given CADOVA_REVEAL_FILES=0, which is upstream's own switch — so a model from somebody else's repository previews quietly without having heard of this app.

go3mf recipes

A recipe is YAML naming the parts of an assembly and the file they are built into. It is the one 3D file here that does not open showing both halves, and both reasons are about cost rather than taste. A recipe is an assembly, so its model is every part's render and a go3mf build on top of them, which is the slowest preview this program has. And whether the file is a recipe at all was decided by reading the head of it — a default that starts that work off the back of a guess is a default that makes opening YAML feel dangerous.

So a recipe opens as its text, with the model offered beside it rather than drawn. What makes it a recipe is a top-level output: and a top-level objects: in the first 8 KB; a repository's other YAML — workflows, compose files, Helm charts — is text and is offered no model at all.

Showing a file never modifies what it is showing. A recipe names the file it produces, and rendering one therefore has somewhere it wants to put a .3mf — beside the source, quite possibly on top of one made by hand. The render happens in a build directory of the viewer's own instead, so the file next to the recipe is left as it is. A recipe whose output: is an absolute path, or climbs out with .., has no such directory that can contain it: that one is not rendered, and the pane says why, rather than being rendered somewhere it was not asked to go.

Nothing renders until somebody looks at it

Rendering a model means running something — OpenSCAD for a .scad, a whole package build for a Cadova model — and it is the tab in front that is worth paying for. So a viewer is built, and any program it needs is started, when the pane has been on screen long enough to mean it, and never merely because a tab exists.

Walking a directory of twenty models from top to bottom renders none of them, and pausing on one renders that one. Twenty opened together — from a search result, or a session restored at launch — render one: the tab in front. A Cadova model behind another tab starts no build and writes no model at all.

A model that would not render shows no model

A render can fail: a .scad with an unclosed bracket, a recipe naming a part that is not there, a machine with no OpenSCAD on it. When one does, the pane draws nothing, and says what went wrong — which for OpenSCAD not being installed is the command that installs it.

Nothing is a deliberate answer rather than an absence of one. The alternative was a lit cube on the build plate, which is what this pane used to fall back to, and it is worse than an empty pane in the one way that matters: somebody who did not write the file cannot tell that the shape on screen is not the shape their code describes. A message alone does not settle it either, because this pane is captured through the viewer's own snapshot, which sees the scene and not the layer above it — so in a screenshot, a bug report, or an agent checking its own work, the shape is the only thing that says whether the load worked. A shape that is not the model is a lie a picture cannot correct.

The file is watched even though it never loaded, so the message is a promise the program keeps: repair the source and the model appears where the message was. The Cadova pane reaches the same answer from different code, and the two agree on purpose — which half of the program draws a pane is not something anybody looking at one should be able to tell from how a failure reads.

The viewer is GoSTL, hosted in an editor tab and pinned at a version rather than taken off whatever copy happens to be on disk. Meshes, the OpenSCAD render and the recipe's assembly all arrive in it, so a shape is looked at the same way however it was described. Nothing here is bundled: OpenSCAD, go3mf and a Swift toolchain are programs with opinions about your machine, and the ones already on it are the right ones — what is missing is named in the pane, with the command that installs it.
