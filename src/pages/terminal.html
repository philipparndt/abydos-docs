Terminal and agents

The terminal is not a strip at the bottom of an editor here. It is where the work happens — shells, tmux windows, agents, a program running in a pod — and the editor, the debugger and the cluster arrange themselves around it.

A real terminal

A PTY with a VT100/xterm emulator over it: full colour, mouse reporting, the alternate screen, and kitty graphics, so a picture printed into a pane is a picture. A Nerd Font is bundled, so a powerline prompt renders without anybody installing anything first.

⌘J opens one and ⌘⏎ gives it the whole window. A pane shows what a command printed even when the command has already finished, and a tab that does not fit is reachable from a chevron that says how many are behind it — on every strip, tmux's own included, where the control used to be computed, reserved and clickable with nothing drawn to say so.

⌘⇧] and ⌘⇧[ move along the strip of whatever column the keyboard is in, so pressed in a terminal they walk the terminal's tabs rather than changing the file behind the panel. And a pane has a pager: this one runs vim, htop, an agent's own full-screen interface and tmux, so git log opens less here as it does in every other terminal on the machine.

tmux's windows as the panel's tabs

Not a tmux-shaped feature of the panel: the strip is tmux list-windows. Opening a window from inside the terminal puts a tab in the strip, closing one takes it away, and renaming one renames the tab — because there is one list and tmux owns it.

abydos some-file.md

Typed in one of these panes, it opens that file in the editor of this window, puts the keyboard in it, and gets the terminal out of the way if it was covering the editor.

The pane's own file descriptor is what says which window asked. Nothing has to be installed, no port is listened on and no lock file is written — the terminal this was typed into is already connected to the window that should answer, and the message goes up that channel as an escape sequence, wrapped for tmux so tmux passes it through.

Agents are sessions, not a sidebar

The app owns the PTY

An agent session is a pseudo-terminal the application owns rather than something a view owns. So it can be hidden, shown again, or handed over for manual takeover, and its process keeps running throughout.

Findings arrive as data

⇧⌘R reviews the branch and ⇧⌘U what is not committed yet. Results come back over a local MCP server as typed data — file, line, severity, detail — arriving as the work proceeds, so a click goes to the line. Scraping a rendered screen would break the first time the tool restyled its output; this is a contract instead.

And work to hand them

The backlog is markdown in state folders that the app, the terminal and an agent all move. An item picked up gets a worktree of its own, and its card reads the progress out of that checkout — on the project page.

What is running, everywhere

Every agent session on this machine already told the app what it was doing: the hook posts an event for each of them, the tmux tabs wear a badge for the session in them, a toast says a line when one in another tab speaks. What none of that answered is the question asked from across the room — is anything waiting for me, and where?

A finished session is not counted, because it waits quietly. A working session that has said nothing for ten minutes is not believed, and one that has said nothing for an hour is forgotten outright — the clock is the last hook event, and hook events bracket a tool call, so a make test is ninety seconds with nothing in between. When nothing is running there is no pill at all, so an idle panel looks as it did.

A row reaches the terminal it is in

Every terminal the panel starts tells its shell which tab it is, and the hook passes that on — or, inside tmux, the pane's own id. So a row opens the tab the session named, in this window or another, or the window and pane of the mirrored tmux session, or switches this panel's client to another tmux session. One the app cannot reach is drawn dimmed and marked elsewhere before it is clicked, and clicking it copies claude --resume <id> — the one thing the app can offer for a session it does not hold.

And says how many subagents are out

A row reads 2 subagents beside what the session last said, and says nothing when there are none, because a count of nought is not news. The count goes up on the tool use that spawns one, down when one hands its work back, and to nought when the turn ends — which is what keeps it honest, since a missed event would otherwise leave a count that only rises.

The order is where, not when

The window's own project first, the rest by name, and within a project the tmux session, the window's index, then the sessions in no window. Recency was the first answer and the wrong one: the list is rebuilt on every hook event and once a second by the staleness clock, and a row that moves while you are reaching for it cannot be clicked. The order is decided when the list opens and held while it is open.

Two limits, said plainly

The hook carries no model name, so the list does not show one. And a session that started before Abydos did, and has sat at a prompt since, has announced nothing to this run of the app: it appears at its next event. For the windows the panel mirrors, tmux's own badge stands in until then.

Every control on the panel's strip lights under the pointer and says what it is in a tip drawn in the app's own type — a title, a line of detail, and the key as a chip — and the key comes from the menu bar rather than from the control, so a tip's promise and a keystroke cannot disagree.
