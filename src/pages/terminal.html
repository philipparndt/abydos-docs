Terminal and agents

The terminal is not a strip at the bottom of an editor here. It is where the work happens — shells, tmux windows, agents, a program running in a pod — and the editor, the debugger and the cluster arrange themselves around it.

A real terminal

A PTY with a VT100/xterm emulator over it: full colour, mouse reporting, the alternate screen, and kitty graphics, so a picture printed into a pane is a picture. A Nerd Font is bundled, which means a powerline prompt renders without anybody installing anything first — the most common way a terminal in an editor announces that it is not the real one.

⌘J opens one and ⌘⏎ gives it the whole window. A pane shows what a command printed even when the command has already finished, and a tab that does not fit is reachable from a chevron that says how many are behind it rather than being unreachable.

tmux's windows as the panel's tabs

Not a tmux-shaped feature of the panel: the strip is tmux list-windows. Opening a window from inside the terminal puts a tab in the strip, closing one takes it away, and renaming one renames the tab — because there is one list and tmux owns it. A pane also does not inherit a tmux socket path that could not exist, which is the failure that used to make a terminal opened inside one of these come up empty.

abydos some-file.md

Typed in one of these panes, it opens that file in the editor of this window, puts the keyboard in it, and gets the terminal out of the way if it was covering the editor. Three things, and the third is what makes it a gesture rather than a background event: opening a file into a pane nobody can see is the same as not opening it.

The pane's own file descriptor is what says which window asked. Nothing has to be installed, no port is listened on and no lock file is written — the terminal this was typed into is already connected to the window that should answer, and the message goes up that channel as an escape sequence, wrapped for tmux so tmux passes it through.

Agents are sessions, not a sidebar

The app owns the PTY

An agent session is a pseudo-terminal the application owns rather than something a view owns. So it can be hidden, shown again, or handed over for manual takeover, and its process keeps running throughout — including while you are looking at something else entirely.

Findings arrive as data

⇧⌘R reviews the branch and ⇧⌘U what is not committed yet. Results come back over a local MCP server as typed data — file, line, severity, detail — arriving as the work proceeds, so a click goes to the line.

Scraping a rendered screen would break the first time the tool restyled its output. This is a contract instead.

And work to hand them

The backlog is markdown in state folders that the app, the terminal and an agent all move. An item picked up gets a worktree of its own, and its card reads the progress out of that checkout — on the project page.

There is a second terminal engine in the build — libghostty-vt, ghostty's state machine with no pty and no renderer of its own — behind a setting that is off, and it stays off here until it has been run for weeks. It is mentioned because it is in the binary either way, not because it is a feature yet: the engine a pane is emulated by is decided when the pane is made, since an engine holds the scrollback, the modes and the images, and swapping one out under a running shell would throw all three away.
