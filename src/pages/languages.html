Languages

Twenty-four are highlighted and folded. What differs between them is everything after that — a server, a debugger, a build tool, a pod — and each of those is a program on your machine rather than something bundled here.

What the columns mean

Highlight and fold come from the grammar; outline is ⇧⌘O without a language server; server is what provides completion, problems and usages; cluster is running and debugging the same thing inside a development pod.

1 jdtls answers for .java. A Kotlin file is highlighted and folded but not served, and its main functions are still found, run and debugged — the JVM does not care which language produced the class.
2 A pom.xml or Gradle build file has no server, so ⇧⌘O over one is answered by that build file's own parser: modules, plugins, dependencies, tasks.
3 Every language folds, by one of two routes. Where the grammar ships a folds.scm — or one is written here, as Java's is — the fold points are the ones that query names. Where it does not, they are derived from the parse tree: any node spanning more than one line.
4 Two servers, and a project says which in .abydos/tools.json. jdtls is type-aware — it reads the build file for the classpath — and importing a five-hundred-bundle reactor is minutes and gigabytes first. kmp-lsp indexes source instead, with no JVM and no type checking at all. On Eclipse's eclipse.platform.ui — 143 bundles, 7,566 files — it was answering go-to-definition across bundles at 2.6 seconds, where jdtls on the same symbol was still silent at ten minutes holding 3.97 GB. Debugging works either way: jdtls is started for the debugger alone when you press Debug.

Nothing is bundled. A language server, a debugger and a build tool each have opinions about your toolchain, and the ones already on your machine are the right ones — so what is missing is named in a bar at the top of the editor, with the one command that installs it.

And nothing has to be installed for a project to be read. What a build file offers comes out of the file, not out of the tool: a BUILD file's *_binary and *_test rules are the targets, and which Conan commands make sense follows from whether there is a conanfile.py or only a conanfile.txt. Neither recipe is executed to ask it what it contains, so running a command without its tool fails the way it always does rather than in a way this has to explain.

Java, in full

The most recent language to be supported end to end, and the one that shows what "supported" means here:

The language server

brew install jdtls. Each project gets an index of its own, and the JDKs installed on the machine are reported to it, so a module targeting 17 compiles against 17.

Or the other one. A repository that is five hundred bundles can say {"languages": {"java": "kmp-lsp"}} and get a syntactic server that has the whole thing navigable in seconds — no JVM, no reactor import, and no type checking at all. Debug still starts jdtls, because the classpath is only there.

Maven and Gradle

Read directly — modules, plugins, dependencies, tasks — so their goals are run configurations and ⇧⌘O works over a build file. The wrapper wins over anything on the PATH.

Debugging

java-debug is not a program but a bundle the language server loads: jdtls is asked for a debug session, answers with a port, and the classpath comes from the same server, because nothing else knows it.

In a cluster

A jar is built here and pushed into a pod that has a JVM. Debugging starts that JVM suspended with JDWP open, so the attach lands before the program has done anything — which is the only way to debug a worker.

Which server, and where from

Where more than one server answers for a language, the project says which it wants, in .abydos/tools.json beside the images: 

{
  "languages": { "java": "kmp-lsp" },
  "kmp-lsp": "pharndt/abydos-kmp-lsp:dev"
}

Two questions, and they stay two on the face of the file: which server, and where it comes from. Settings say the same for one person across every project, and the file wins where both speak — a checked-in answer is a statement about the project.

The footer at the bottom of the editor says which server actually answered and what chose it. A server that is here and not ready says so there too: a Swift package whose dependencies have not been built reads sourcekit-lsp — preparing rather than claiming it cannot read the project. Nothing is hidden while it says that — the errors stay where they are.

The toolchain the project says it wants

Out of a devcontainer

A checkout carrying a devcontainer.json can have its language servers run inside that container, so the problems on screen are the problems from the build rather than from whatever this Mac happens to have installed. Asked for once per project, and undone or moved to another of the project's containers from a pill beside the project's name.

Or out of an image the project names

.abydos/tools.json names an image per tool and is checked in, so a machine that never installed the tool gets the same answer as everybody else. An image that is not here is fetched before the tool is first used; one this app ships a recipe for is built on the machine rather than pulled.

Pinned, and told before anything starts

A project can pin the toolchain a server runs against — a Rust channel, a JDK — and a project pinning one the image has not got is told so before a container is started, rather than after a server has come up and answered wrongly for ten minutes.
