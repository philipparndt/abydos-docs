Git

One button, one tree, and two pages that open at the size they are given. Every verb sits on the row that draws the thing it acts on.

One tree

⌘2: the working copy, the stashes, local branches, each remote, the tags, the worktrees and the submodules.

  • Branch names fold on /, and a slash is always a folder — a tree that changes shape with the count is one you have to look at twice.
  • ⌘F filters, and flattens the tree while it does.
  • The working copy, origin and Tags arrive shut. The question this pane is asked is where am I.

The repository is the first row, and it is the button. It says how far you are from the upstream — 2 behind · 1 ahead, upstream gone, detached at 8d9ac24b — and does the verb that follows: fetch when level, pull when behind, push when ahead. A Fetch sits beside it whenever there is a remote, because that is wanted exactly when the count on the row is stale. It stays put while the tree scrolls.

What a branch row says

The end of every row is one column, and what sits in it is either news or a standing fact. 

main ✓            ↑2 ↓1     two to push, one to pull
feature/api          ↑3 ☁︎↑  three commits of its own, never published
old-thing              ☁︎✗   its remote branch was deleted
shipped                 ✓    already merged — the row is dimmed too

A merged branch is dimmed, not moved

Where a branch sits is how it is found. One that moves when it merges is one you hunt for; one that disappears vanishes at the moment it becomes safe to delete. The tick keeps its colour, because it is the reason the row is grey.

An unpublished branch is measured differently

Its upstream counts are nought and nought — the same thing a branch in step with a remote reads — so it is measured against the default branch instead. Only the ahead half is drawn: ↓ here means waiting to come down, and it is not borrowed to say anything else.

Order, and one order

The current branch and the default are pinned on top, then folders. Tags come newest first, because alphabetical order lies about versions: v1.10 before v1.9. The titlebar's branch pill follows the same order — two lists of the same branches in one window do not get to disagree.

And a branch can become a pull request

Publish and Open Pull Request… on a branch the host does not have, Open Pull Request… on one it does. Two steps as one verb, because having to know the push comes first is what makes this the part people leave the app to do.

Several branches delete at once, under one dialog written from what was found: already on main, nothing would be lost, or not on main, these would lose commits. Ancestry decides which, not git branch -d — that refuses a branch ahead of its own stale upstream even when every commit on it is already on main. A branch a worktree holds offers to take the worktree with it, with the disk it would free beside it.

Two pages

⇧⌘L opens the log and ⇧⌘K the commit, each as a tab in the editor. Neither rearranges the window: the panel's height and the tree's width are somebody's own arrangement.

A log scoped to a branch is one git log of both tips, so the commits the upstream has and the branch does not are in it, dimmed. A repository saying 1 behind used to open a log with no trace of what there was to pull. Folding a merge takes its lanes with it, and commit messages render as markdown.

The working copy row reads Review 2 changes… rather than Commit…, which would read as commit now when nothing is committed by pressing it. Changes are the folders they changed, not a flat list of paths: a folder stages everything under it. Staging answers the click — the row switches sides on the command's own exit, and the status re-read confirms it.

Nothing destroyed without being said

Switching over uncommitted work, discarding, resetting, rebasing, amending, deleting a branch that is ahead and moving a tag each say what they will cost — leading with a number, because "4 commits leave main" is read and "this cannot be undone" is not — and leave a real branch under backup/ first. A toast names it and offers to undo.

  • A branch, not the reflog. Reflog entries for unreachable commits expire and gc collects what they pointed at. Not a private namespace either: safety nobody can find with git branch is not safety.
  • Untracked files are captured too. git stash create has no --include-untracked, so it would have insured a discarded file with a commit not containing it.
  • One question for a whole estate, and one report naming each repository and its backup ref. Asking two hundred times is asking nobody.
  • Force-pushing is the one thing not insured, and it says so. No local ref recovers somebody else's commits from a remote.

When git has stopped in the middle

It says which branch is coming in and where it is going. Rows tick green as they clear, the line under the headline counts 2 of 3 resolved, and Continue lights when the last one turns — so the disabled button never needs a sentence explaining itself. Continue, Skip and Abort end the operation; a rebase can be carried to its end here.

Never "ours" and "theirs" on screen. Stage 2 is --ours in both a merge and a rebase and they are opposite halves: rebasing replays your commits onto somebody else's. Use Ours during a rebase throws away the wrong half and the wording does not say so.

Git forgets, so the pane remembers twice. A path stops being unmerged the moment it is staged, so a list built from what is unmerged now shrinks instead of ticking. The pane also reads what git wrote under # Conflicts:, so a merge reopened tomorrow still counts what was already dealt with.

A stash you can read

Review… opens a stash in the commit page's shape — files, diff, read-only. Finding out what a week-old one held used to mean applying it over a clean working copy, which is the one move somebody with work in progress cannot make.

Untracked files come with it, from git's third parent, and they are the half somebody has forgotten they had. Which is why putting the working copy aside takes them by default, and that is not git's default. Each stash says whether it would still apply, checked without touching the working copy; where it would not, branching from it is offered instead.

The message

Drafted from what is staged

Not from the working copy, and with this repository's last twenty subjects alongside. It fills two fields and stops: nothing staged, nothing committed, both fields still editable.

In the format the tooling reads

Conventional Commits, because changelogs, releases and version bumps all key off it. A toggle turns it off. What comes back is never rewritten into the format — prepending a type classifies somebody's change on their behalf.

Twenty messages back

A history control beside the summary opens the last twenty subjects, and choosing one fills both fields with that commit's whole message.

And it survives leaving

A commit message is the most expensive text here to lose: written once, from a diff just read. It travels in the project's session, and a draft that lands after a switch goes to the project that asked for it. Onto a message with words in it, a draft is offered rather than thrown away.

Diffs, everywhere one is shown

  • Git's preamble is not drawn. Every pane showing a diff has a tree beside it with one row selected, so it has already said which file this is. What is kept is git's guess at the declaration the hunk is inside, drawn as a labelled rule. A one-line change went from eight rows to three.
  • Both sides, side by side, a run of removals paired with the additions that follow it. Old and new line numbers throughout, and selected lines stage, unstage or stash on their own.
  • A file's own row compares. Against Last Commit is staged and unstaged edits in one answer; History… opens the log scoped to that file, where a commit then offers Compare with Working Copy.
  • And a picture diffs as a picture. A changed screenshot used to diff as No textual changes. — true, and useless. Both sides are drawn on the editor's checkerboard: side by side, overlaid with a slider, or with the regions that differ outlined and counted.

An estate is one working copy

A refactoring across a microservice estate is done in a superproject holding two or three hundred repositories as submodules. ⇧⌘M answers where is this refactoring: a row per service with what changed, its branch, how far that is from its remote, and its pull request — ordered by what needs something, because three hundred alphabetical rows of which four matter is a page nobody reads twice.

What was asked, on an estate of 200 servicesSeconds
What the app used to run on every filesystem event1.57
The superproject alone, --ignore-submodules=dirty0.09
git submodule status, the obvious replacement5.31
All 200 asked at once, twelve concurrent0.45
The inventory, one ls-files --stage0.01

So one question became two, and the ceiling of twelve is measured rather than chosen. After the first read nothing is swept: every submodule's git directory lives under the superproject's own, so a write inside one service re-reads that service alone.

A commit across repositories reports itself per repository and never claims to be atomic. Nothing makes two hundred commits one transaction, and the rollback that would pretend otherwise is git reset --hard in repositories somebody may already have fetched. A failure at the fourth of six leaves five commits standing, says which, and is resumable.

Reviewing somebody else's branch is the pull requests page. What the editor's gutter says about the lines you have changed is the editor page.
