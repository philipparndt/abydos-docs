Git

One button, one tree, and two pages that open at the size they are given. Every verb sits on the row that draws the thing it acts on — which is the rule that says what belongs here and what does not.

One tree

⌘2: the working copy, the stashes, local branches, each remote, the tags, the worktrees and the submodules. Branch names fold on /, so feature/lights and feature/blinds sit under one row — and a slash is always a folder, even holding a single branch, because a tree that changes shape with the count is one you have to look at twice. Typing into the filter (⌘F) flattens the whole thing: a tree you have to expand to reach a name you have just typed is worse than no tree.

The working copy arrives shut, and origin and Tags arrive shut with it. Every change unrolled under the first row pushes the branches off the bottom of a column, and the question the tree is usually asked is where am I rather than what have I changed — which is what the commit page is for. The remote's branches and every release there has ever been are somebody else's account of things, and unrolled they are the bulk of the pane.

The repository is the first row, and it is the button. It says how far the branch you are on is from its upstream — 2 behind · 1 ahead, level, upstream gone, detached at 8d9ac24b — and does the verb that follows from that: fetch when level, pull when behind, push when ahead, with a Fetch beside it whenever there is a remote, since fetching is the one thing you want exactly when the state on the row is stale. It says when the remote was last asked, which is one stat of .git/FETCH_HEAD and no subprocess. And it stays put while the rest of the tree scrolls: how far you are from the remote is state, and state that scrolls behind forty branches is state nobody reads.

What a branch row says

The end of every row is one right-aligned column, and what sits in it is either news or a standing fact. 

main ✓            ↑2 ↓1     two to push, one to pull
feature/api          ↑3 ☁︎↑  three commits of its own, never published
old-thing              ☁︎✗   its remote branch was deleted
shipped                 ✓    already merged — the row is dimmed too

A merged branch is dimmed, not moved

Where a branch sits in the list is how it is found, so one that moves when it merges is one you hunt for, and one that disappears vanishes at the moment it becomes safe to delete. The tick keeps its colour: it is the reason the row is grey, and fading the answer along with the question leaves nothing on the row saying why.

An unpublished branch says how much is on it

Its upstream counts are nought and nought, which is exactly what a branch in step with a remote reads — so it is measured against the default branch instead. Only the ahead half is drawn: ↓ on this pane means waiting to come down, and borrowing it to say "main has moved on" would read as the first thing on every other row. That figure is in the tooltip, in words.

Order, and one order

The branch you are on and the repository's default are pinned on top, then branches in no folder, then a section each. Tags come newest first, because alphabetical order lies about versions — v1.10 before v1.9. Right-clicking a section header offers the orders and remembers the choice. The titlebar's branch pill follows the same one: two lists of the same branches in one window do not get to disagree.

And a branch can become a pull request

Publish and Open Pull Request… on a branch the host does not have, Open Pull Request… on one it does — two steps as one verb, because having to know that the push comes first is what makes this the part of the job people leave the app to do. Reviewing one is a page of its own.

Several branches can be selected and deleted at once, under one dialog written from what was found rather than from what was asked — already on main, nothing would be lost, or not on main, these would lose commits, with the names and a count under each. Whether anything would be lost is decided by ancestry against the branch you are standing on, not by git branch -d, which refuses a branch that is ahead of its own stale upstream even when every commit on it is already on main. A branch a worktree holds offers to take the worktree with it, with the disk it would free measured beside it.

Two pages

The two things you sit down to do are not panes in a column three hundred points wide. ⇧⌘L opens the log and ⇧⌘K the commit, each as a tab in the editor — and each leaves the window arranged the way you had it, because the panel's height and the tree's width are somebody's own arrangement, chosen for what they were doing a minute ago.

A log scoped to a branch is one git log of both tips under --date-order, so the commits the upstream has and the branch does not arrive already merged into the sequence — dimmed as one piece, the row, the dot and the line down to the commit they were built on. A repository whose own header says 1 behind and whose log showed no trace of what there was to pull was telling somebody deciding whether to pull that there was nothing. Folding a merge hides its commits and takes its lanes with it. Commit messages render as markdown, which is what they are written in.

Committing is reached from the working copy row, and the row does not say Commit… — that reads as commit now, after a confirmation, and nothing is committed by pressing it. It says Review 2 changes…, which names what happens next, and the context menu and ⇧⌘K say the same words so the three ways in cannot drift.

Changes are shown as the folders they changed rather than as a flat list of paths: a folder stages everything under it and says how much of itself is on this side of the index, with the counts in a column so the plus signs do not step in and out by a digit at every level. Staging answers the click — the rows switch sides on the command's own exit, and the status re-read that follows confirms or corrects it. The selection is kept across the rebuild, and where the row it was on has gone it lands on the nearest surviving one.

Nothing destroyed without being said, and nothing lost

Switching a branch over uncommitted work, discarding, resetting, rebasing, amending, deleting a branch that is ahead and moving a tag each say what they will cost — leading with a number, because "4 commits leave main" is read and "this cannot be undone" is not — and leave a real branch under backup/ before they run. A toast afterwards names it and offers to undo.

A branch, and not the reflog

Reflog entries for unreachable commits expire and gc collects what they pointed at. Not a private ref namespace either: safety nobody can find with git branch is not safety. The backup/ folder keeps its shape however few refs are under it, and can be swept by age with the count of what each age would take shown before you choose.

Uncommitted work is captured without being disturbed

git stash create was the obvious way and is the wrong one: it has no --include-untracked, so discarding a file git had never seen would have been insured by a commit not containing it.

One question for a whole estate

Every repository backed up before any file is discarded, and one report naming each repository and its backup ref. Asking two hundred times is asking nobody — and do not ask again is keyed per repository, since an answer given while looking at one service is not a decision about two hundred.

The one thing that is not insured

Force-pushing a branch, and it says so. No local ref can recover somebody else's commits from a remote.

When git has stopped in the middle

It says which branch is coming in and where it is going, rather than a short hash and the truncated subject of somebody else's commit. Each row ticks green and strikes through as it clears, the line under the headline counts 2 of 3 resolved, and Continue lights when the last one turns — so the disabled button never needs a sentence explaining itself. Continue, Skip and Abort are the three verbs that end one, and a rebase can be carried to its end from here.

Never "ours" and "theirs" on screen. Stage 2 is --ours in both a merge and a rebase and they are opposite halves: rebasing replays your commits onto somebody else's, so the branch you are on arrives as --theirs. A menu item saying Use Ours during a rebase throws away the wrong half and nothing in the wording says so.

Git forgets, so the pane remembers twice. A path stops being unmerged the moment it is staged, so a list built from what is unmerged now shrinks instead of ticking. The pane holds the set for one stop and also reads what git wrote under # Conflicts: in .git/MERGE_MSG, so a merge reopened tomorrow still counts the files already dealt with. A file whose markers have gone but which is not staged says edited in amber — the one state with no other signal on screen.

A stash you can read

A stash used to be a commit nobody could read: a list of file names and no way to find out what was in it short of applying it over a clean working copy, which is the one move somebody with work in progress cannot make. Review… opens one as a page in the commit page's shape — the files, the diff beside them, read-only, because a stash has already happened.

Untracked files come with it. Git keeps them in a third parent, and they are exactly the half somebody has forgotten they had — which is also why putting the working copy aside from its own row takes them by default, and that is not git's default: the file you have just written is both the one you are most likely putting aside and the one still untracked. Each stash says whether it would still apply, checked without touching the working copy, and where it would not, branching from it is offered instead — applied on the commit it came from, it cannot conflict.

The message

Drafted from what is staged

Draft writes a summary and description from the staged diff — not the working copy — with this repository's last twenty subjects alongside. It fills two fields and stops: nothing staged, nothing committed, both fields still editable. That the diff is sent is said once, per project, before the first time.

In the format the tooling reads

The summary is asked for as Conventional Commits v1.0.0 states it — <type>[scope][!]: <description> — because changelogs, releases and version bumps all key off it. A toggle turns it off, and with it off the prompt is byte for byte what it was. What comes back is never rewritten into the format: prepending a type is classifying somebody's change on their behalf.

Twenty messages back

A history control beside the summary opens the repository's last twenty subjects; choosing one fills both fields with that commit's whole message. One git log -20 when the menu opens.

And it survives leaving

A commit message is the most expensive text in the app to lose: written once, from a diff that has just been read. Both halves travel in the project's session, and a draft that comes back after you have switched projects lands in the project it was asked for rather than in the one now on screen. Onto a message with words in it, a draft is offered — the button turns red and reads Use draft instead — rather than thrown away.

Diffs, everywhere one is shown

Git's preamble is not drawn. diff --git, index and the two ---/+++ lines say which file this is, and every pane showing a diff has just said that — there is a tree beside it with one row selected. What is kept is the text after the @@, git's guess at the declaration the hunk is inside, drawn as a labelled rule. A one-line change went from eight rows to three.

The two sides can be drawn beside each other, a run of removals paired with the run of additions that follows it. Old and new line numbers are both shown. Selected lines can be staged, unstaged or stashed on their own. A file's own row offers Compare ▸ Against Last Commit — staged and unstaged edits in one answer, not two — and Compare ▸ History…, which opens the log scoped to that file, where a commit then offers Compare with Working Copy.

And a picture diffs as a picture. A changed screenshot, icon or exported diagram used to diff as one line: No textual changes. True, and useless. Both sides are read from git and drawn on the same checkerboard the editor uses, each labelled with what it is and its pixel size — side by side, or overlaid with a slider, or with the new one dimmed and the regions that differ outlined and counted. The comparison is arithmetic in the kit, with a channel threshold so a re-encode is not a change, and a plain refusal with a reason for two pictures of different sizes.

An estate is one working copy

A refactoring across a microservice estate is done in a superproject that holds two or three hundred repositories as submodules. ⇧⌘M is the page that answers where is this refactoring: a row per service with what changed in it, the branch it is on, how far that is from its remote, whether the superproject records it somewhere else, and its pull request. Ordered by what needs something — conflicted, changed, ahead, moved, then the quiet ones — because three hundred alphabetical rows of which four matter is a page nobody reads twice.

What was asked, on an estate of 200 servicesSeconds
What the app used to run on every filesystem event1.57
The superproject alone, --ignore-submodules=dirty0.09
git submodule status, the obvious replacement5.31
All 200 asked at once, twelve concurrent0.45
The inventory, one ls-files --stage0.01

So one question became two, and the ceiling of twelve is measured rather than chosen: twelve concurrent read 200 in 0.45 s and twenty-four read them in 0.46 s, and unbounded is three hundred git processes against ten cores while a build is running. After the first read nothing is swept — every submodule's git directory lives under the superproject's own, so two watchers cover three hundred repositories and a write inside one service re-reads that service alone.

Every verb is aimed at the repository that owns its path, which is what makes a submodule's file stageable from the superproject at all. A commit across repositories reports itself per repository and never claims to be atomic: nothing can make two hundred commits one transaction, and the rollback that would pretend otherwise is git reset --hard in repositories somebody may already have fetched. A failure at the fourth of six leaves five commits standing, says which, and is resumable. Pull requests across the estate are one set keyed by branch, read from the forge every time and never stored.

Reviewing somebody else's branch is the pull requests page. What the editor's gutter says about the lines you have changed, and who last touched them, is the editor page.
